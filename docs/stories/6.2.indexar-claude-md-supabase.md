## Story
**As a** sistema teamAI,
**I want** que cada projeto tenha seu CLAUDE.md indexado no Supabase com patterns extraidos,
**so that** o CrossProjectContextProvider tenha uma base de dados para calcular similaridade entre projetos.

## Acceptance Criteria
1. Tabela `user_projects` atualizada com campos `claude_md` (text) e `patterns` (jsonb).
2. Sync automatico quando CLAUDE.md e salvo/atualizado no projeto.
3. Patterns extraidos do CLAUDE.md: decisoes arquiteturais, padroes de codigo, tecnologias usadas.
4. Indice de busca por similarity criado (full-text search ou embedding index).
5. API endpoint `/api/projects` lista projetos do usuario com patterns.

## Dev Notes
Contexto tecnico relevante:

### Schema existente
A tabela `user_projects` ja esta definida na arquitetura (secao 5):
```
user_projects: (user_id, project_name, claude_md, patterns)
```
Esta story garante que esteja criada e populada no Supabase real.

### Estrategia de indexacao
- **Full-text search** (v1): `tsvector` nativo do Postgres. Sem dependencia externa, bom para keyword matching.
- **pgvector** (v2): extensao do Supabase para embeddings. Mais preciso para similarity semantica, mas adiciona complexidade.

Recomendacao: v1 com full-text search. Migrar para pgvector quando CrossProjectContextProvider migrar para embeddings (Story 6.1 v2).

### Extracao de patterns
O parser de CLAUDE.md deve ser robusto o suficiente para extrair informacao util sem ser fragil a mudancas de formato. Focar em:
- Headers (## ) como indicadores de secao
- Keywords de decisao: "chose", "decided", "pattern", "convention"
- Listas de tecnologias: frameworks, linguagens, tools

### Testing
- Schema: migration aplica corretamente
- Parser: extrai patterns de CLAUDE.md real do teamAI
- Sync: atualiza quando muda, ignora quando nao muda
- API: autenticacao e RLS funcionam
